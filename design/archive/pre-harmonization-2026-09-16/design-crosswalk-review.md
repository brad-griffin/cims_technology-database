## Vocabulary the names need

Naming follows section 5: `-` within a component, `_` between. With the carrier now a list on the row rather than a name component, a design technology is named `equipment_discriminator`.

**20 equipment terms** are not in section 6.2 and would have to be added, or the labels renamed onto existing terms:

`adsorber`, `annealing-furnace`, `binder`, `coating-line`, `drilling-rig`, `flare`, `fracturing-fleet`, `gas-treatment-unit`, `haul-truck`, `heat-exchanger`, `hoist`, `liquefaction-train`, `mobile-equipment`, `paste-plant`, `photovoltaic-array`, `pickling-line`, `separator`, `turboexpander`, `well`, `wind-turbine`

**356 discriminators** are not existing variant or carrier terms. Section 6.2 treats a new term as a modelling decision, so the options are to add them, to widen the variant list into a free discriminator, or to shorten the names.

## What adoption would change

1. `build-template.py` -- `SECTORS` gains `biofuels` and `oil-and-gas`; `END_USES` is replaced by the 73 design rows and gains a `sector` column, so `end-use.csv` becomes sector-scoped. `service-unit` and `temperature-tier` come from the design table's `service-unit` and `heat-tier` columns.
2. Section 6.2 of the design document -- the equipment terms listed above, and a decision on the discriminators.
3. `populate.py` -- `END_USE_UNIT` is read from the design table rather than held as a dict; `node_for` keys on the design end use; the roster is seeded from the design technology table, so `add_tech` attaches a source's technology to an existing design row instead of creating one. `design_doc_roster()` (section 4 of the design doc) is superseded by the design technology table.
4. `aggregate.py` -- R2 and R4 are subsumed: the design table already says which end uses are cross-sector and already holds the carrier as a list, so the roster does not grow the names those rules exist to collapse. R3 (`other-services`) and R7 (`unquantified`) stay. R5 and R6 stay for the extraction rows, which still arrive spelled as their source spells them.
5. `build-cims-map.py` -- the `review` and `fuel-node` rows behind the empty end uses above have to be placed, and the mapper's end-use table now targets the design vocabulary.
6. The crosswalk tables in `design_crosswalk.py` and the names in `design_names*.py` become the adoption rules; the two CSVs beside this file are their output.

## Found while crosswalking

- **`ccs` is in both the carrier and the variant vocabulary** in section 6.2, so `aggregate.split_name` files it in whichever component it reads first: 0 of the 36 roster names ending `_ccs` carry it as the energy carrier and the rest as the variant. The design doc already notes this for `oxyfuel-ccs`; plain `ccs` has the same problem. Until it is fixed, anything keying on the variant column misses those rows -- this script reads the carrier back.
- **R2 has already merged away a distinction the new end uses need.** The generic end uses were collapsed onto `cross-sector` with no process step, so `Natural Gas.Production.Supply.Extraction.Compression`, `...Processing.Compression` and `...Transmission.Compression` are one application row with a joined `reported-steps` cell, while the design table puts them in three different end uses. CIMS placements here are therefore resolved from `cims-map.csv` by branch, not from the merged application row. An adoption pass has to do the same.
- **One efficiency bucket sits on a node it does not belong to.** `rolling-mill_efficiency-moderate` reaches `mining` / `separation-and-processing` through a mining forming-and-finishing node, which is why that end use is the only one taking a roster efficiency bucket with no efficient variant of its own. The design table is not missing an option here; the extraction filed a rolling mill in mining.
- **`Petroleum Crude.Steam` is claimed twice** -- by `oil-and-gas` / `in-situ-bitumen` in its `cims-services` cell, and by the cross-sector heat bands. The integral-vs-supplied rule and that row's own `heat-delivery` cell ("draws heat-medium-temp") both say the steam system is cross-sector, so that is where this crosswalk puts it, and `in-situ-bitumen` is left with only the CIMS In-Situ rows, which the mapper has not placed.
